# Claude Fable 5.2 · 提示词消化笔记与结论

> 基于官方《Prompting Claude Fable 5.2》整理的作者笔记，含概括与改编，不收录官方文档的连续译文段落或症状→处方原文；非官方文档、无厂商背书，API 参数与价格以官方现行页为准。核对日期 2026-11-15。本仓库没有作者在 Fable 5.2 上的 A/B 评测数字；下文若提到测试结果，均来自官方指南，不得当作本仓库的实测。

## 一、消化笔记

### 1. 仍然是排障表：没看到症状就别加

Fable 5.2 指南按观察到的行为分节。官方建议的迁移顺序也是：先显式设定 effort，先审从 Fable 5.1 或 Opus 5.5 带过来的旧指令，再对实际出现的早停、多余审批、长轮沉默、过量委派等逐条补丁，并测量效果与 token 成本。这和 5.1 笔记里的「先减后加」同向。

### 2. Effort：默认 high，不要搬旧扫描结果

官方 API 默认是 `high`。档位名跨模型排序相同，但同一档的思考量可以不同，所以不要把在 Fable 5.1 或 Opus 5.5 上调好的档位直接搬过来，应在自己的评测上重扫。

官方对档位的定性（须用自己的任务验证）：`low` 适合快问快答、规格清楚的任务和高吞吐（例如偏执行的子代理）；`medium` 适合交互式编码、对话和日常知识工作；`high` 适合困难编码、研究、agent 工作和长无人值守（官方称这一档的轮次明显长于 `medium`）；`xhigh` 留给已经测出收益的最难长程工作；`max` 用于测天花板，或时间与 token 都不计较的少见任务（官方举例是开放的科学与数学问题）。

官方称：多数能力收益发生在用到 `high` 时；从 `medium` 升到 `high` 在其跟踪的多数编码和知识评测上有提升，但也更费 token 与时间——自己的评测站得住，就回到 `medium`。`high` 以上的收益不均匀、视任务而定。低/中档的 agent 工作更容易提前结束，若出现再补「把任务做完」类指令（见下）。`high` 及以上几乎每条回复前都会思考，包括打招呼；基本请求觉得慢或贵，就降低该轮 effort。官方测试中，「直接回答、不要细想」这类句子在 `medium` 及以上拦不住思考，应降档而不是加这类句子。Effort 几乎不影响回复长短，长短靠提示词。

产品侧建议（实施前再核官方现行页）：多数团队应先从 Opus 5.5 起步，只有在更高 effort 上的评测仍不够时，再升到 Fable。

### 3. 长任务提前结束：先观察，再补「做完」

多步任务上，5.2 有时会在工作未完成时结束一轮（列出剩余、提出继续，或停在超时这类普通障碍上），低/中档更常见。若真实出现，再在系统提示里补「未完成的工作不要停；普通障碍先诊断再处理；真正的硬阻断要说明并另找安全路径」这类指令。这不覆盖高风险或破坏性动作的确认。官方在其产品回放、`medium` 档的测试中称：补了类似文本后，本可继续却早停的会话大约减半；主动征求许可或提出「要不要继续」的结束大多消失，但「列出剩余然后停」这类结束并未去掉；输出 token 约增加 30%。模型会更少发问，所以高风险或不可逆动作仍要保留你自己的确认步骤。

催它继续时，写明要做什么，不要只回「继续」。审批规则要具体到动作。官方测试中，把「向对话外的人发消息」写成须审批的步骤后，模型连约一半日常同事沟通也按下了。

### 4. 先说清代码是谁的——而且这条副作用不小

官方称 5.2 很在意代码归属。提示未说明、或把代码库写成别人的时，它倾向在现有结构上追加，即使造成重复；写成「由它长期维护、设计由它做主」时，更常合并重复，有时还会做没被要求的相邻修改。官方在小编码任务上的测试称：加了这句后，合并重复从不足一成升到约七成半，但输出 token 约增 70%–80%，并出现未要求的测试、文档，有的运行还改了已有行为；收尾的 PR 摘要常漏掉小改动，需要对照 diff。用户自己拥有代码、希望尽量少改时，不要加这句。只写「禁止顺便重构」压不住它：官方测试中，即使前面有这样的范围限制，过半运行仍会合并重复。

写任务契约时：只有当你真的希望它改结构时才写归属，不要把它当成默认套话。

### 5. 长轮次看起来像沉默：先检查客户端，再补更新

工具调用之间的进展写在 progress-update 的 `thinking` 块里；默认 `thinking.display` 为 `"omitted"` 时文本是空的，只渲染 `text` 块的客户端会像没有输出。需要可见更新时，再按官方页改 `display`（`"updates"` / `"summarized"`，部分为 beta）。交互场景才需要频繁更新；官方也建议 5.2 适合没人需要频繁汇报的长程异步工作。具体 harness 提醒与系统提示补丁见官方页，补了会增加一些可见文本。

### 6. 子代理：先看你的 harness，不要先改工具描述

委派量取决于 harness 和任务。官方称：在几乎没有引导的短任务上很少起子代理；在本身就鼓励委派的编码产品里则很积极。`xhigh` / `max` 上，官方看到 5.2 会派子代理复查自己的工作，同样任务上 5.1 没有。早期测试者把它当规划/编排器效果不错；并行能加速，但子代理可能占掉会话成本的很大一块，要确认子代理默认用的是哪个模型。

只有在模型起的子代理明显多于任务所需，而且现有提示已经在邀请委派、子代理又占了很大 token 时，才改子代理工具描述：写清成本、何时值得/不值得、以及怎样给子代理写简报。官方在 `high` 档测试中称，更长、侧重成本的描述大约把子代理数量减半。若系统提示、skill、agent 文件里已有「要委派」的常驻句，先审这些句子。

### 7. 不要让谨慎指令堆起来

记忆、笔记和规则文件会从旧会话攒下过时禁令（例如「不要重试」）。5.2 跟得紧，就可能频繁要一个并不需要的审批；官方称多代理一起工作时更明显。处理：删不再需要的旧指令；点名哪些例行步骤不必审批（只说「大胆做」太含糊）；收窄「一出错就停」这类会阻断无人值守的条件；把「永不」改写成带范围的规则（例如「删除文件前先确认」，而不是「永不删文件」）。高风险或不可逆动作仍要你自己的确认步骤。

### 8. 从 Fable 5.1 / Opus 5.5 迁过来时先减旧补丁

官方点名若干在前代有用、在 5.2 上可能加成本、有副作用或不再有效的做法（均须用自己的任务验证）：

- 常驻「要委派」的句子：若测试里委派过多，先删。
- 把 token 预算写进提示词给模型看：预算大小会影响 5.2 花多少；官方在 `high` / `xhigh` 编码任务上称，去掉很大的预算后成本下降、表现相当。这说的是提示词里的文字，不是 API 的 task budget（官方测试未覆盖后者）。
- 改写已经发出的 system / tools / 更早消息：5.2 使用保留的 thinking，前缀对不上时默认会 400（或在 Batch 中丢块）。除官方提供的 context editing / compaction 外，历史只追加；中途改指令放在最新一轮。
- Opus 5.5 聊天场景那两句「先前的回答就当作做完了」：官方称在 5.2、`high` 档会减少跟进问题的思考，而且更不容易主动指出自己先前的错。若你希望它复查旧结论，不要带这句。
- 「直接回答、不要细想」：5.1 通常会听；5.2 在 `medium` 及以上拦不住思考。删掉，改降 effort。
- 过硬的文风上限（例如一句不得超过若干词）会让行文破碎；先删再考虑「让报告好读」类补丁。
- 迁之前清理记忆和笔记里已经过时的绝对禁令。

### 9. 长任务的收尾报告要让没看过工具过程的人读懂

官方称，读最终报告的人通常没看过工具调用和打开过的文件，报告需要自洽：关键点靠前，少用过程中自造的简称，一句一个意思。这只在读者需要看报告或交接时才补，不要当默认套话。

## 二、可带走的结论

1. **没症状不加指令**：先设 effort、先减从 5.1 / Opus 5.5 带来的旧补丁，再对实际症状加一句。
2. **默认 `high`，但先问要不要用 Fable**：官方建议多数团队先从 Opus 5.5 起步；档位不要从旧模型原样搬来。
3. **低/中档更容易早停**：先观察，再补「把任务做完」；普通障碍与故意设置的阻断要分开；高风险动作仍要你自己的确认。
4. **不要默认宣称「你拥有这份代码」**：只有真想让它改结构时才写；副作用（多改、多 token、摘要漏改）很明显。
5. **长轮次沉默先查 `thinking.display`**，再决定要不要加更新指令；5.2 也适合不需要频繁汇报的异步长任务。
6. **子代理先审你现有的「请委派」句子**，再改工具描述；并确认子代理用的模型。
7. **谨慎指令会堆积**：迁模型前先清理记忆和过时的「永不」。
8. **本仓库没有 Fable 5.2 的作者 A/B 数字**，不能把 2026-09 在其他模型上的结果直接套过来。
