# GPT-6 / GPT-6.1 家族 · 提示词消化笔记与结论

> 基于官方《Using GPT-6》整理的作者笔记，含概括与改编，不收录官方文档的连续译文段落；非官方文档、无厂商背书，API 参数与价格以官方现行页为准。核对日期 2026-11-15。官方页写明：文中提示词最佳实践针对的是在 GPT-6 Astra 上观察到的行为，换到 6.1 Sol / 6.1 Terra / Luna 时要用自己的工作负载再评估。本仓库没有作者在 GPT-6.1 上的 A/B 评测数字，也不能把 2026-09 在 Astra / GPT-5.6 上的数字当成 6.1 的成绩。

## 一、消化笔记

### 1. 家族怎么选（官方口径，不是本仓库评测）

官方把现行 GPT-6 家族分成几档，实施前按官方模型页复核：

- **GPT-6 Astra**（`gpt-6-astra`）：最吃重的工作。不支持 reasoning effort `none`。
- **GPT-6.1 Sol**（`gpt-6.1-sol`）：复杂工作、成本更低。同样不支持 `none`。官方还为它提到 Responses Multi-agent beta，以及把 `reasoning.context` 设为 `all_turns` 以复用先前相容的思考。
- **GPT-6.1 Terra**（`gpt-6.1-terra`）：官方《Using GPT-6》页的短标签是视觉推理与写作；计算机使用是该家族沿用的既有能力，产品说明里也常和 Terra 一并提到，实施前按模型页复核。约 2026-10-26 发布。支持 `none`。官方模型页上的默认 effort 为 `medium`（实施前复核）。
- **GPT-6 Luna**（`gpt-6-luna`）：焦点明确的高吞吐任务。支持 `none`。
- 仍存在的 **GPT-6 Sol**（`gpt-6-sol`）：支持 `none`。从它迁到 `gpt-6.1-sol` 时，若原 effort 是 `none`，官方建议改用 `low`，并把在 Chat Completions 里调函数的请求迁到 Responses API。

截至 2026-11 中旬，GPT-5.6 系列仍有官方文档，但已不是默认的现行一代；若执行层仍在用 5.6，见同目录 `gpt-5.6.md`。Astra 的 2026-09 消化笔记见 `gpt-6-astra.md`，下面不重复当时的价格对照。

### 2. 迁移：effort、Responses API、不要搬旧扫描

能保留的有效 reasoning effort 就先保留，用原来的代表性任务建基线，再按实际退化打补丁。两处不能原样搬：

- **没有 `none` 的型号**：Astra 与 6.1 Sol 不支持 `none`，应改用 `low`。若旧请求用的是 `minimal`，官方建议先从 `low` 比起，在代表性任务上对比。Terra、GPT-6 Sol、Luna 支持 `none`。
- **工具调用走 Responses API**：Astra、6.1 Sol、6.1 Terra 虽支持 Chat Completions，但工具调用必须用 Responses。GPT-6 Sol 与 Luna 只在 `reasoning_effort: "none"` 时能在 Chat Completions 里做 function calling；带推理的工具调用仍用 Responses。

另外几条迁移时容易漏掉的 API 层约束：effort 不是 `none` 时去掉 `temperature` / `top_p` / `top_logprobs`；对话中途改 effort 用 `configuration_update`，并保持请求级 `reasoning.effort` 不变，以保住前缀缓存；从 GPT-5.5 及更早迁缓存参数时，把 `prompt_cache_retention` 换成 `prompt_cache_options.ttl: "30m"`（细节以官方缓存页为准）。从 GPT-5.6 Terra 迁到 6.1 Terra 时，官方要求在相同 effort 上用有代表性的图像和工作流对比两边，不要假设观感或成绩自动继承。

本仓库没有 6.1 家族的作者评测，上面这些是官方迁移步骤，不是「迁了一定更好」的保证。

### 3. Astra 上观察到的偏移（其他 6.x 须自测）

官方把下面几条写为 GPT-6 Astra 上的行为，并提醒在你选用的型号和工作负载上评估后再采用对应补丁：

- **更爱问、可能停得早**：协作取向更强，额外输入若会实质改变结果，它更常发问；用户以为它会做合理假设并做完时，就可能停住。
- **指令跟得更紧，也更易被 skill 带偏**：对 skill、`AGENTS.md` 等文件里的指令更敏感。官方强烈建议审计模型能读到的这些文件。
- **回答偏详细、爱格式化**，并可能跨会话重复某些套话。需要散文或特定结构时，要把风格写清楚。
- **委派可能偏少**。需要并行时，要写清何时、以及委派多少。
- **编码任务上测试偏彻底**；小改动可能被测得比任务所需更宽。

这些是写任务契约时最值得盯的偏移，但不是已经在 6.1 Sol / Terra 上复测过的作者结论。

### 4. 写任务契约时能直接用的几条

下面几条是官方针对上述偏移给出的处方方向，适合写进契约或 skill，而不是整段照抄官方示例提示词。采用前应在目标型号上观察是否真有该症状。

- **已授权的工作偏向做完**：用户在说「帮我做 / 我想…」时，把它当作动手的指令，不要停在「我可以做」、计划书或「要不要继续」。范围里可逆、只读、或上下文已经授权的动作继续推进；破坏性或不可逆的动作仍要停。
- **先做出可审的具体结果，再请求批准**：批准应当对着已经做出来的东西，而不是对着一个尚未开始的计划。不要因为假想风险额外加警告、免责或审批流程。
- **用户指令优先于 skill**：若 skill 导致暂停、询问、留下未完成工作或偏离用户意图，点名具体文件与条文，并区分明确要求和自己的解释。指令文件很多时，这条有助于把沉默的冲突翻出来。
- **需要并行就写清委派**：官方称 Astra 能把工作分给并行子代理，但可能派得比你需要的少；在你的 harness 里用一句话说明「什么情况下应该派」。
- **验证要有停止条件**：对低影响、可逆、测试只会镜像实现本身的改动，不要为测而测；该做的检查通过后，只有新改动、失败或未解决风险才扩大或重跑测试。这和本协议 §2「验收通过且输入未变就交付」同向。
- **文风按交付物写，不堆通用禁令**：需要少列表、少套话时再点名；不要预先贴上很长的禁用词表。

若模型在并不需要批准的步骤上反复停下来，优先查上面这几条是否写清楚，而不是再加一层「要主动」的空话。

### 5. 和 2026-09 Astra 笔记的关系

`gpt-6-astra.md` 里关于指令优先级、委派不足、验证停止条件、写作风格的判断，与现行《Using GPT-6》页仍然同向，本文不再展开。那一篇里按当时价格做的「每完成任务成本」对照，2026-11 未重核，不能直接沿用。现行页还增加了异步工具调用、中途转向、`configuration_update`、6.1 Sol 的多代理与跨轮思考复用等 API 能力；写契约时一般不必把这些写进提示词，按官方页在 harness 层启用即可。

## 二、可带走的结论

1. **先按官方分工选型，再在自己的任务上验证**：Astra 吃重、6.1 Sol 复杂且更便宜、Terra 偏视觉/写作/计算机使用、Luna 偏高吞吐；这不是本仓库的评测结论。
2. **Astra 与 6.1 Sol 没有 `none`**；从 `none` / `minimal` 迁过来时官方建议先从 `low` 比起。Terra 支持 `none`，官方模型页默认 `medium`。
3. **Astra / 6.1 Sol / 6.1 Terra 的工具调用走 Responses API**，不要假定 Chat Completions 能原样承接。
4. **官方提示词处方首先针对 Astra 的偏移**：更爱问、易被 skill 带偏、委派偏少、小改动可能测过头。换到 6.1 要自测，不要把补丁当默认套话。
5. **写契约时优先写清：做完的条件、何时不必再问、用户指令与 skill 的优先级、验证的停止规则。**
6. **本仓库没有 GPT-6.1 的作者 A/B 数字**，不能把 2026-09 在 Astra / GPT-5.6 上的结果直接套过来。
