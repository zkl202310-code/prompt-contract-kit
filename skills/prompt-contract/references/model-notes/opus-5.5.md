# Claude Opus 5.5 · 提示词消化笔记与结论

> 基于官方《Prompting Claude Opus 5.5》整理的作者笔记，含概括与改编，不收录官方文档的连续译文段落；非官方文档、无厂商背书，API 参数与价格以官方现行页为准。核对日期 2026-11-15。本仓库没有作者在 Opus 5.5 上的 A/B 评测数字；下文若提到测试结果，均来自官方指南，不得当作本仓库的实测。

## 一、消化笔记

### 1. 大多数团队的起点，不是「先上 Fable」

官方产品建议（实施前再核现行页）：多数团队应先从 Opus 5.5 起步，只有在更高 effort 上的评测仍不够时，再升到 Fable。官方也写：已有的 Opus 5 提示词通常不必先改就能用，*Prompting Claude Opus 5* 的写法仍是合理起点；本笔记只记 5.5 特有、写任务契约时用得上的差异。

官方指南对编码、知识工作、视觉与计算机使用有一组对比 Opus 5 的测试陈述。本文不把那些陈述转述为作者结论，也不当作本仓库评测。写契约时只需记住操作含义：官方把默认档放在 `medium`，并称在这一档上，它跟踪的部分编码和知识评测已经比得过或超过 Opus 5 的 `high`。

### 2. Effort：默认 medium，thinking 始终开着

Effort 是调节智力、延迟和成本的主开关，因为 thinking 始终开着。官方 API 默认是 `medium`（Opus 5 默认是 `high`），应显式设定，并在自己的评测上试几个档，不要把 Opus 5 上用的档位原样搬来。档位名跨模型并不对应同等思考量。

官方称：在同一档上，Opus 5.5 每轮往往比 Opus 5 想得更多，尤其是 `xhigh` 和 `max`。若保留给 Opus 5 设的 effort，要预期更长的轮次和更多输出 token。三个对应调整：

- `max_tokens` 要给思考 token 留出空间——即使思考内容不返回给你，思考也计入 `max_tokens`。按「关闭 thinking 的 Opus 5」定的上限可能把回复截断。官方称，长的 agentic 编码轮次用该模型上限 128,000 比较稳妥。
- `xhigh` 和 `max` 留给已经测出质量收益的工作。
- 想减少思考，先降 effort；降档比在提示词里写「少想一点」更可靠。

对话中途改顶层 `effort` 会让已缓存的消息失效；若要在同一会话里改档并保住缓存，按官方页使用 per-message effort（beta）。

### 3. 从「关闭 thinking」的 Opus 5 集成迁过来

Opus 5 在 `high` 及以下允许 `thinking: {"type": "disabled"}`；Opus 5.5 对此返回 400。若旧集成是关着 thinking 跑的，官方给出四条配套改动：

- 先从 `low` 起步再测。`low` 档会把思考压短；会不会几乎不思考取决于你的提示词，要在自己的流量上测延迟与质量，质量下降再回到 `medium`。若首 token 时间仍然关键，可以再试「直接回答、不要细想」这类句子，并同时测质量——少思考可能降低质量。这一点和 Fable 5.2 不同：Fable 5.2 上同类句子在 `medium` 及以上拦不住思考，应改降档。
- 删掉「把推理写进回复正文」这类曾用来代替 thinking 的指令；改从 summarized thinking 块阅读理过程。要求模型在回复里复述内部推理，可能被 `reasoning_extraction` 类拒绝。
- 重测当初为「关闭 thinking」准备的缓解指令；thinking 始终开着之后，有的已经不必保留，「不要思考」类规则则应删掉。
- 按块类型读回复，不要假定第一条一定是 `text`；默认 `display: "omitted"` 时，开头的 `thinking` 块文本是空的。

### 4. 无人值守不要把一则文字汇报当成任务结束

长任务上，Opus 5.5 会边做边更新；有些更新以纯文本结束一轮（`stop_reason: "end_turn"`），并不带工具调用。把这种结束当成任务完成的无人值守循环，会在这里停住。官方建议：把它当作汇报，而不是完成证明；用清单或待办跟踪未完成项；若一轮结束时仍有未关闭项且未声明阻断，再发一条点名这些项的短消息让它继续；同一任务上自动续跑两三次仍无进展就停，交给人看。已启动的后台命令或子代理尚未返回时，也不要当任务已完成。

系统提示里可以点名你不想看到的早停类型（例如只总结下一步却不行动、在并不阻塞的问题上等用户、把「该汇报了」当成停点），同时写清真正该停的情况（没有用户输入就无法推进，或阻断是故意设置的）。这类补丁只适合真正无人值守的场景，不要加进有人在场、需要问答的应用；它会让模型在本该停下来问的地方继续做，所以高风险或不可逆动作仍要保留你自己的确认步骤。预期每任务的工具调用和输出 token 会多一些。中途把这段加进 `system` 会改前缀并作废先前的 thinking 块，应从会话第一轮就放好，或按官方页用追加方式改指令。

### 5. 进展更新、多应用先探查、时间信号——按需再加

工具调用之间的进展同样写在 progress-update 的 `thinking` 块里；默认 `display` 为空，只渲染 `text` 的客户端会像没有输出。需要可见更新时，再按官方页改 `display`。交互场景若要「动手前说一句、结束时给独立短复盘」，再写进系统提示。长轮次仍然过静时，由 harness 在连续若干步无可见文本后追加一句提醒，而不是在提示词里预先堆很多「要汇报」的规则。

在跨多个应用（邮件、文档、表格、CRM）的松散任务上，官方称加一句「动手前先广泛查看任务未必点名的相关来源，并依据所见行事」会提高完成正确性，代价是略多的工具调用和 token。因为模型会按读到的内容行动，检索范围里不要放不可信内容。

多代理编排里，Opus 5.5 对已用时间很敏感。能估计工期就给一个略宽的时间预算，并在每次回传时附上已用时间；给不出合理预算时，只展示已用时间，并加一句「能省的时间不要花」。官方称预算主要是让更多代理并行，和降低 effort（那会减少工作本身）不是一回事。预算是建议性的，到点不会强制停下；需要硬停止时用你自己的超时。时间压力下模型可能少搜、少验证一点，要在自己的任务上检查回答质量。

### 6. 聊天与粘贴文本的两个小补丁

聊天应用的系统提示若还有「先仔细想再回答」一类句子，官方建议在 Opus 5.5 上考虑删掉：思考量主要由 effort 控制。官方在其聊天产品测试中称，删掉后回复开始得更早，未见明显的质量下降。

多轮聊天里，模型有时会在思考新消息（哪怕是短跟进）时回头复查旧答案，从而增加后续轮次的思考和延迟。若希望它把先前的回答当作已完成，可以在系统提示末尾加两句「除非用户问起或指出问题，否则把注意力放在当前问题上」。官方称这会减少跟进轮的思考、让回复开始得更早；但在长分析、或后续步骤可能暴露先前错误的 agent 任务上不要加。它也可能让模型更少主动指出自己先前的错，采用前要测这一点。Fable 5.2 指南对同一写法更谨慎，见 `fable-5.2.md`。

用户消息里若常粘贴可能带指令的外部文本，可用成对标签标出粘贴块，并在系统提示里写清：只有用户自己的话要求执行时，才遵循粘贴块里的指令。官方提醒这只是与其他防注入措施并用的一道护栏，标签可被仿造，也可能让模型略更谨慎，要在自己的任务上测量。

### 7. 视觉脚手架与前端默认风格要重测

官方称 Opus 5.5 在不额外使用工具时，读图表、示意图和截图比 Opus 5 更准，先前为视觉输入搭的脚手架应重测是否还需要。最密的输入上，更高分辨率（尤其是技术图纸）以及裁剪/测量类图像工具仍然有用；这些工具在更高 effort 上更有效。不借助工具时，升档有助于读技术图纸，对图表帮助不大。

做前端却没有设计方向时，它会落到少数默认风格上；只写「不要看起来像套模板」往往只是从一种默认换成另一种。更有效的是点名不要用的具体模式，再根据第一稿实际用了什么迭代补充。不要把这种清单写成与任务无关的固定套话。

## 二、可带走的结论

1. **先把它当作默认起点**：官方建议多数团队先用 Opus 5.5（默认 `medium`），评测不够再考虑 Fable。
2. **thinking 始终开着**：关 thinking 会 400；从旧集成迁过来时先从 `low` 测起，并给 `max_tokens` 留出思考空间。
3. **同一档位名不等于 Opus 5 的同一思考量**：不要原样搬旧 effort；想少想就先降档。
4. **无人值守要区分「汇报」和「做完」**：纯文本结束一轮不是完成证明；自动续跑要有次数上限；高风险动作仍要你自己的确认。
5. **多应用、时间预算、聊天里的「旧答案当作做完」都是按需补丁**，各有代价，先观察再加。
6. **本仓库没有 Opus 5.5 的作者 A/B 数字**，不能把 2026-09 在其他模型上的结果直接套过来。
